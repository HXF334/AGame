# 资深开发者开发规范

严谨的资深工程师原则：**最小改动、可验证、可回溯、不破坏现有功能**。
本规范优先级高于所有业务技能 —— 任何代码生成、修改、调试操作都必须遵守。

<!-- SOURCE-NOTE:BEGIN -->
> **⚠️ 唯一权威来源（2026-10-24）**
> 本文件是 `senior-dev-standard` 的**唯一来源**。
> Workshop 版 `~/.openclaw/agents/work/agent/workshop-skills/senior-dev-standard/SKILL.md`
> 是**由本文件自动生成的同步镜像**（`scripts/sync-skills.js`）。
> 改规范就改本文件，然后跑同步脚本；**不要单独改 Workshop 版**。

## 1. 代码修改铁律

### 1.1 先读后改，禁止全量覆盖
- 修改任何文件前，**必须先完整读取原文件内容**。
- 只修改用户明确指定的函数、段落、行，**无关代码一行不动**。
- 保留原有代码的注释、缩进、命名风格，**不擅自重构**。

### 1.2 最小改动原则
- 能改一行就不改整个函数，能改一个函数就不改整个文件。
- **禁止因为一个小 bug 重写整个模块。**
- 禁止修改用户未提及的文件、配置、依赖。

### 1.3 红线文件
未经明确指令，**永远不修改**：`app.json`、`project.config.json`、全局配置文件。
**不擅自新增 npm 依赖、第三方库、外部链接。**

### 1.4 改坏就回滚，不要在半坏状态上叠补丁
- 改动跨行正则/字符串模式时，**写死 `\n` 的模式在 CRLF 文件上必然失配** → 先数目标文件的实际行尾（CRLF / 裸 LF），再决定 split 的分隔符；
  **写回时保持原行尾**，别把 LF 文件改成 CRLF（微信小游戏打包器不容忍，见 `wechat-minigame-ui` §7）。
- **正则里带中文字符的模式** → 用 `split/join` 精确串，不用跨行正则。
- 替换包裹括号时，**捕获组不能含左括号**，否则多出未闭合括号。
- 改坏立刻 `git checkout` 回滚重来，**不要在半坏状态上继续叠补丁**。

**完成判据**：改动后 `node --check` 立即通过；失败就回滚，不叠补丁。
**批量改文件后回读结构**（行数 / 最长行 / 关键锚点）—— 脚本自报 `OK` 只证明它执行了，不证明结果完好；
细见 `wechat-miniprogram-fix-class` §3。

### 1.5 改源码的默认动作：`edit` 工具优先于补丁脚本

**规则**：改动已存在的 `.js` / `.md` 源码，**默认用 `edit` 工具**做精确整段替换；补丁脚本只在 `edit` 确实定位不到（编码 / BOM / 不可见字符）时才写。

**为什么（实测）**：两种写法的**失败形态不同**——`edit` 的 oldText 匹配不上会**报错并停下**（改动不落盘）；
补丁脚本按行号 / `splice` 替换**失配时静默截断或只替换首行**，写出的文件语法合法、测试也可能照过，
直到人眼或后续改动才暴露。本项目一晚连写 7 个补丁脚本，**每一个都有坑**（数组被 `splice` 压成一行、
只替换首行留下孤儿行、漏字段、漏逗号、工具函数只认字符串却传了数组）；同期 `edit` 一次没错过。
**差别不是「哪个更好写」，是「哪个失配时会吵」。**

**配套闸门**：每次写入后**立刻** `node --check`（改了 `.md` 就回读该段）——
本项目正是靠这条闸门在提交前抓住全部脚本事故，没有一次坏代码进仓库。

## 2. 自动测试规范

### 2.1 写完必测
任何函数新增/修改后，必须自动生成对应测试用例，覆盖三类：**正常场景、边界场景、异常场景**。
每个用例写明**输入、预期输出、实际结果**。针对游戏逻辑必须包含极端用例（空牌、重复牌、特殊牌型）。

> **[2026-10-23 用户授权修正]** 原「纯 JS 用原生 console.assert、不引入测试框架」一条已撤销 ——
> 本项目事实：推风 bug **复发两次**，两次修复期间全量回归始终全绿却抓不到，
> 因为历史推风测试全部直接调 `doPushWind()` **绕过了被修改的触发层**。
> **没有套件化回归 = 修改没有验证。**

### 2.2 变异测试是「测试有效」的唯一硬证据
改完必须能回答：**「哪个测试会因为这个 bug 而失败？」** 答不出 = 没测。

把修复退回，确认那条断言**精确失败**（不是全挂、不是误报），再恢复。
**只有「通过」不能证明断言有效。**

**「答不出」要落实成一次 grep**：把该 bug 依赖的状态变量名在测试目录里搜一遍，
零命中 = 没有断言覆盖 = 等同于没测（实测 56 套件全绿而某显示 bug 坏了 5 版）。

> **函数级单测测不到传参错误** —— 函数正确而调用方传错，单测必然全绿，**必须真的驱动调用方**。

### 2.3 审查看「调用点」而非「模块」
本项目 `src/` 15 模块 100% 有直接测试且从未出事；**三次 bug 全在 `game.js`**。
审查看**调用点**。

### 2.4 测试纪律：改一点只跑直接覆盖的套件
| 改动范围 | 跑什么 |
|---|---|
| 单个函数内部 | 直接覆盖它的 1~2 个套件 |
| `game.js` 流程控制（return / 提前退出 / 状态推进）| 该流程涉及的套件 |
| `src/` 某个模块 | 该模块的套件 + 1 个端到端 |
| 一次改多条 / 改公共契约 / 重构 / **大任务收尾** | **全量** |

**一次全量 ≈ 一次大任务的收尾动作**，不是每个小改动的例行动作。
全量会把真正要看的信号淹没，也掩盖了「这次改动到底被谁覆盖」。

> **反例（2026-10-24 晚）**：每改一点 UI 就跑全量 55 套件，一天跑了七八遍。
> 规则早写在 `AGENTS.md`，**写了没执行等于没写**。

**判定结果先读输出、再看退出码**：长回归被环境回收时常见「退出码 1 但输出全绿」——那是**会话被回收**，
不是测试失败。先读输出里的 `passed/failed` 计数再下结论。

**同一验证不重跑第三次**：被回收就**换拿结果的方式**——脚本落盘 → 分块跑 → 逐个跑；换姿势重跑只是多烧几轮。

## 3. 工作流程标准

1. 接收需求后，**先分析影响范围**，明确要修改的文件列表。
2. 读取相关文件的现有代码。
3. 给出修改方案：**改哪里、怎么改、影响什么**。
4. 执行修改，**只改动目标部分**。
5. 自动生成并运行测试用例。
6. 输出修改总结：改了什么、测试结果、注意事项。
7. **改 Skill 集合的流程**（本项目每个 Skill = 仓库源 + Workshop 镜像，**两处**）：
   - **源** = `da-a-game/skills/<name>/SKILL.md`（唯一来源）；
     **镜像** = `~/.openclaw/agents/work/agent/workshop-skills/<name>/SKILL.md`（自动生成，**勿手改**）。
   - 改**源** → 跑 `node scripts/sync-skills.js` 生成镜像 → 跑 `--check` 校验（不一致时退出码 1）。
   - **frontmatter（`name` / `description`）不走同步**：脚本的 frontmatter 取自**镜像自身**。
     源里改 `description` 不会传到镜像 → **源与镜像必须同时改**，否则触发词不生效。
     `name` 决定加载路由，**不可改**。
   - 目录别名：仓库 `da-a-game-rules` → 镜像 `dada-a-game-rules`（见 `scripts/sync-skills.js` 的 ALIAS 表）。
   - `node scripts/preflight.js` 第 8 项就是「镜像一致性」闸门。

## 4. 诊断纪律

- **先证伪自己的探针，再碰规则函数和源码**（详见 `game-ui-engine-contract` §2.3）。
- 探针夹具本身要先验证（构造器签名错了会**静默失效**，测的其实不是那手牌）。
- 审查脚本报「有测试覆盖」不构成有覆盖的证据 —— **注释不是断言**，反向断言是防回归，
  只有正向断言才算覆盖。
- 断言依赖正则/日志文案时先确认它**真的能匹配上** —— 永不命中的正则 = 恒真断言 = 看起来有断言、实际什么都没验。
- **同一症状连续两版没修好 → 停止加条件，换定位方法**。在同一处反复加条件会把门控越堆越厚；
  UI 显示类问题改做**门控链枚举**（见 `game-ui-engine-contract` §2.4）。
