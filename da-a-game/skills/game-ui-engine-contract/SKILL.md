# 画面接引擎的契约排错

## 适用

引擎侧测试全绿（无回归），但**界面/AI 驱动层**表现为：无响应、元素缺失、同一内容重复、元素在屏外。

**归属判断**：规则逻辑错 → `dada-a-game-impl`。IDE 配置/编译错、WeChat `utils/*.js` 模块缺导出且有大量调用方 → `wechat-miniprogram-fix-class`。本文只管**调用方与引擎之间的形状与推进契约**。

---

## 1. 先冻边界事实，再改代码

改之前先打印一次实际值，10 秒消除整类猜测。写个临时 `.js` 跑，不要 `node -e` 内联（PowerShell 会切碎引号/括号，见 `windows-cn-batch-encoding`）：

```js
// tests/_probe.js，跑完删
const idx = require('../src/index.js');
const ai = require('../src/ai.js');
console.log('index exports:', Object.keys(idx).join(', '));
console.log('ai exports   :', Object.keys(ai).join(', '));
console.log('engine.chooseAction =', typeof idx.chooseAction);   // undefined 即转发漏了
console.log('sample action:', JSON.stringify(ai.chooseAction(/* ... */)));
```

判据：调用点写的每个 `engine.X` 都能在上面列表里找到；AI 返回值每个字段名与引擎入参一一对应。任一不满足，先补边界再谈逻辑。

## 2. 症状 → 根因对照

| 症状 | 根因 | 定位 | 修法 |
|---|---|---|---|
| `X is not a function` | 引擎入口没转发导出：子模块导出了、`src/index.js` 的导出列表里没有 | 打印 `Object.keys(require('./src/index.js'))` 与调用点比对 | 调用方直接 `require('./src/ai.js').X`；或在入口补转发 |
| AI 一直不出牌 / 每回合都失败 | 动作**形状**对不上：驱动层返回平铺 `{ type, playerId, cardIds }`，引擎要 `{ type, payload: { ... } }` | 打印一次真实返回值，逐字段对照引擎入参 | 加包装层，payload 键只带引擎认识的名字（如 `playerId` / `cardIds` / `choice`），其余丢弃 |
| 出完牌后画面死、按钮点了没反应 | 驱动循环在动作失败时 `break`，回合停在失败者身上，再没人推进 | 读循环体，找 `break` 与早退 | 循环加 `guard++ < 200`；失败改**强制 PASS + `continue`**，绝不 `break`。强制 PASS 也失败才停 |
| 轮到别人时手牌整排消失 | 可见性条件里混了交互条件（`isHumanTurn && hand.length > 0`） | 渲染函数里搜 `isHumanTurn` / `phase ===` | 渲染无条件；命中框（hitbox）只在人类回合注入 |
| 同一条信息显示两遍（两个"桌:"） | 上次改显示时新块加了、旧块没删 | `Select-String -Path game.js -Pattern '桌:\|tableStr\|tStr'` 按内容找全部渲染点 | 按内容定位两块，删旧块；删完重跑该 grep 确认只剩一处 |
| 列表"写了没显示" | 末行越过画布：`base + (n-1)*step >= H`；或未越屏但压到交互区 | 手算第 n 行 y，并对比交互区上沿 | 压 base/step 或减行数；行数/间距/起点三者联动，见 §2.1 |
| 用户报"引擎违反了规则"，但规则函数单测就是对的 | 报告描述的牌面 ≠ 引擎实际处理的牌面，或出牌走的是另一条路径 | 探针只喂用户描述的牌，逐层打印识别结果 | 先证实实际出的牌；引擎已正确就**不改规则函数**，见 §2.2 |

### 2.1 列表/日志几何：行数 × 间距 × 起点 联动

```
末行 y = 起点 + (n - 1) × 间距
```

- **两条上界都要查**：`末行 y < H` **且** `末行 y < 交互区上沿`（按钮行常在 `H*0.93`）。只查 H 会得到"没出屏、但压在按钮上"
- **可读性下界**：`间距 × H` 必须大于字体像素，否则字形视觉上粘连，用户会报"太挤"。本项目 13px 字体实测 `0.023*H ≈ 14px` 偏挤 → 提到 `0.029*H`
- **加行数必然要压间距或抬起点**，先算再改。本项目：起点 `H*0.55` + 间距 `0.029H` 配 15 行时 `末行 = 0.55 + 14×0.029 = 0.956H`，已越过按钮行 `0.93H`
- **buffer 长度 = 能显示的最大行数**。改了它，越界判定里的 `n` 要同步换算，别只改一个数

### 2.2 用户报的规则违规复现不了时

**先证伪自己的假设，再碰规则函数**。规则文是唯一来源，改它需要用户明确同意——不要把诊断当成修复：

1. 建探针直接调规则函数，**只喂用户描述的牌**，打印每层识别结果（`identifyHand` → `canBeat` → handler）。先确认导入路径与导出名真实存在：`tests/` 下的探针用 `../src/...`；拿不准就先列目录 + `Object.keys(require(...))`。**再确认要测的特殊属性真的被设上了**（打大A 的大A 靠 `card.is主方大A` 标志，构造器签名错了会静默失效，见 §2.3）
2. 夹具已证实真实、规则函数仍返回正确结果 → 问题不在规则函数。继续查：实际出的牌是不是用户以为的那两张？出牌走的是不是同一条路径？**UI 的 log 文案能不能区分规则区分的牌型**（对A 与 双大A 在文字上极易看成一回事）
3. 探针用的牌与实际出的牌不一致时，**先修探针的牌再重新判断**，不要在探针结论上直接改引擎

### 2.3 探针/grep 三个方向的结论都不足为据

**方向 A：探针说引擎没问题，不构成引擎正确的证据**

**已撤销的教训（2026-10-21）**：本项目曾据"对A 含一个大A，`canBeat` 返回 `false`，引擎正确"判定不必改规则函数，随后证明是探针夹具造假——`createNormalCard(suit, rank, X)` 的第 3 参是 **id**，被当成了 opts，于是 `is主方大A` 始终 `false`，测的其实是**普通对A**。引擎确有一个真 bug：`compareHands` 的 PAIR/TRIPLE 分支用了含大A 加成的编码，导致对A 压过对3（修法见 `dada-a-game-impl` §3）。

**下结论前先验证夹具本身**：

| 探针写法 | 静默失效 | 改成 |
|---|---|---|
| `createNormalCard('H', 14, { is主方大A: true })` | `id: "H-A-[object Object]"`、`is主方大A: false` | 建牌后 `c.is主方大A = true` |
| `canBeat(cardsA, cardsB)` 传裸牌数组 | 两边 `.type` 都是 `undefined` → 比较恒为 0 → **恒 false** | `canBeat(identifyHand(A), identifyHand(B))` |

先打一行 `assert(造的牌.is主方大A === true)`，再跑规则断言。**两个方向都返回 false 几乎总是参数形状错，不是规则**；真 bug 通常只在一个方向错。

**方向 B：探针/审查脚本报引擎有 bug，同样不构成引擎有错的证据**

对源码做正则断言（`不含 X` / `不得出现 X`）是审查套件的常规做法，但它匹配的是**子串**，不是语义。子串撞名就会报出一条不存在的 bug：

| 断言 | 撞到的实际内容 | 处置 |
|---|---|---|
| `draw 不展示底牌` | `fillText('底牌公开: 是/否')` —— 这是**公开的布尔状态标记**，人人可见，与底牌明面无关 | 收紧为「不访问 `.底牌` 对象」，再看代码确认无渲染调用 |
| `不出现 draw()` | 注释里的 `draw()` 字样 | 剥离注释或改用更精确的锚点 |

处置顺序：
1. 断言失败后，**先打印命中的那一行原文**（grep 出上下文几行）再下结论；不看行就改引擎，等于按猜测改代码。
2. 问「这条断言想禁止的是什么行为」——如果实际代码是那个行为的**合法、非泄露版本**（状态标记 vs 牌面），就是断言写窄了，收紧断言而不是改代码。
3. 同一条 `X` 命中多个含义时（`底牌` vs `底牌公开`），断言必须能区分二者，否则它会长期以误报形式消耗信任。
4. **读代码侧同一个坑**：`Select-String` 扫源码会连注释一起命中。审计一个修复时，先剔除注释行再数实际代码行——实测查一个非法常量，前 6 处命中全是自己写的说明注释，真代码在 7 行之后。`Get-Content f.js | ? { $_.Trim() -notmatch '^(//|/\*|\*)' }` 再数。

**方向 C：审查脚本报告「有测试覆盖」，同样不构成有覆盖的证据**

用规则手册的必测用例清单反查测试文件，是覆盖对账的常规做法。但命中数只说明「文件里出现了这个词」：

| 命中情况 | 真实含义 |
|---|---|
| 命中 0 个文件 | 只说明没有用这些措辞。测试里的措辞常与规则原文不同（实测规则写「自动为主方」，测试里是 `FORCED_CHECK` / 「兜底」），**词形不同 ≠ 没测** |
| 命中 N 个文件 | 只说明有文件提到。**注释不是断言**，反向断言（`!== 'DEFAULT_HEART'`）是在防回归，只有正向断言（`=== X` 或把它喂进被测函数）才算覆盖 |
| 命中几乎全部文件 | 说明特征词太泛（「取牌」「过牌」），该信号在这个粒度上没有区分度 |

**结论必须由人工读断言代码得出**：把命中行连上下文打印出来，逐条判断是「注释 / 反向断言 / 正向断言」。任何自动化覆盖报告都要附这一步，否则「20 条全覆盖」可能只是 20 条都提到了同一个泛词。反过来，工具报出的**空结果和误报都不能直接当结论**——先给工具植入一个已知坏例，确认它抓得住，再信它的通过。

**正向断言也可能恒真（空断言）**：断言依赖正则或日志文案时，先确认它**真的能匹配上**。实测一条 `OUT_RE` 要求日志行以玩家名开头，而实际格式是 `  → 戊 AI 出完牌 ...`，正则永不命中 → 断言恒真 → 看起来有断言、实际什么都没验。**加一条前置断言证明被观测的事件确实被捕获**（如「出完牌事件被成功识别」），再让它去驱动目标断言；没有这条前置断言的产出型断言，默认视为未验证。

三个方向合起来一条规则：**先证伪自己的探针，再碰规则函数和源码；自己的断言也要先证伪再采信。**

## 3. 只报"已修"的锚点

**锚点验收规则见 `wechat-miniprogram-fix-class` §3（权威处）**：每个锚点各自打印 `OK` / `NOT FOUND`，
跑完读完每一行再汇报；任何 `NOT FOUND` 都要如实写「这条未改成 + 已重新定位锚点」，
不要因为其它锚点 `OK` 就整条报修完。

**本 Skill 补的一条**：锚点全 `OK` 只说明**字符串替换成功**，不说明**行为正确**。
改 `game.js` 的 UI 段落后，验证入口是 §5 的无头测试 —— 锚点全绿但 UI 行为变了，仍算没验完。

## 4. 收尾四件事

1. `node --check` 每个改过的 `.js` 全绿
2. **先跑「直接覆盖你这次改动」的套件，不要每次都全量。** 全量回归是**大任务收尾**的动作，
   不是每个小改动的例行动作 —— 全量会把真正要看的信号淹没，也掩盖了「这次改动到底被谁覆盖」。
   **映射表**：改单个函数内部 → 覆盖它的 1~2 个套件；改 `game.js` 流程控制（return / 提前退出 /
   状态推进）→ 该流程涉及的套件；改 `src/` 某模块 → 该模块套件 + 1 个端到端；
   改公共契约 / 重构 / **交付或冻结版本前** → 全量。
   **回答不了「哪个测试会因为这个 bug 而失败」= 没测** —— 那种情况跑全量也抓不到。
   要跑全量时，套件数不变、0 FAIL（新增套件则报新数字）。一行拿到 PASS/FAIL 名单：
   ```powershell
   node --check game.js; $p=0; $f=0; foreach ($t in Get-ChildItem tests/test-*.js){ node $t.FullName *> $null; if ($LASTEXITCODE -eq 0){ $p++ } else { $f++; $t.Name } }; "suites: $p PASS / $f FAIL"
   ```
   **被 exec 切断后先 poll，不要重跑**。全量回归（几十套件）常被判定为长任务并切到后台，调用直接返回“still running”。此时用 `process poll`（`timeout: 30000`）能拿到**已经跑完的完整结果**。实测同一命令重跑 4 次都是被切断，而 poll 一次就全部返回。判断依据：`process list` 里还有这个 session 就别重跑——重跑不改变切断行为，只是白白多烧几轮。
   分块（每块 8~10 个套件）可以降低单次时长，但块大小不是决定因素，**总时长才是**；切断后先缩小块也解决不了，先 poll。
3. 批量对局跑一遍（本项目 `tests/test-perf.js`），确认没有局触顶步数上限——驱动循环死循环只在批量局里暴露
4. **IDE 可用时让用户目视确认**。四类里只有**跑到屏外（几何）**真的测不出来；死锁、元素消失、重复显示**先走 §5 的无头测试**——它比目视快、且能留下可复跑的证据。别拿"要目视"当作不写自动化测试的理由。

## 5. IDE 不可用（或不想等 IDE）时：无头 UI 测试

UI 文件是唯一有真实状态机和渲染的一层，**引擎测试全绿完全不代表它活着**。宿主 API 很少时可以 mock 掉，在 node 里驱动**真实 UI 函数**（`doPlay`/`doPass`/`runAI`/`draw`），拿到与 IDE 同级的信号。

**先量宿主依赖面**再决定投不投入——这一条决定成本上限：

```powershell
Select-String -Path game.js -Pattern '\bwx\.[A-Za-z]+' | ForEach-Object { $_.Matches.Value } | Sort-Object -Unique
Select-String -Path game.js -Pattern 'ctx\.[A-Za-z]+' | ForEach-Object { $_.Matches.Value } | Sort-Object -Unique
```

本项目实测：`wx.createCanvas` ×1、`wx.onTouchStart` ×1、ctx 方法 9 个。小到 30 行 mock 就覆盖得了，于是值得做。面很大（几十个 API）就停下——那已不是 mock 的成本区间。

**mock 形状**（scaffold 与测试骨架见 `references/headless-ui-harness.md`）：`install()` 注入 `wx` 并返回记录器（全部 ctx 调用**含实参** + 已注册触摸处理器），`fireTouch(handlers, x, y)` 触发处理器，`uninstall()` 还原。**必须记录实参**——只返回 noop 的 mock 只能验"没崩"，验不了任何渲染性质。

**导出块必须含 `draw`。** UI 文件通常已有 `typeof module` 守卫的测试导出块，但常常恰恰漏了最该测的 `draw`（本项目就漏了）。不导出 `draw` 则渲染层完全不可测。不导出 `draw` 时**不要**退而用调用总数间接推断（见 §5.2）。守卫已存在时补导出对微信运行时零影响。

### 5.1 断绝对不变量，不要断阶段快照

`runAI()` 是 init 末尾调的**同步 while 循环**（`guard++ < 200`），require 返回时 AI 回合已打完。任何"每家 21/22 张"式的阶段快照必然失败，而**失败原因是测试写错，不是代码错**：

| 断言 | 真实原因 | 改成 |
|---|---|---|
| `require` 之后断每家 21/22 张 | init 末尾 `runAI()` 已同步打完 AI 回合 | 断绝对不变量：每家 ≤ 22、牌张守恒 108 |
| 用整局**累计** canvas 调用数判断渲染范围 | 累计量随步数增长，与单帧无关 | 取**单帧**切片再判断（§5.2） |

推论：**驱动循环必须能跑到终局**。设 guard 步数上限，跑到 `GAME_END` 为止，**每步**复核守恒。整局驱动是无头测试相对 IDE 最大的价值——作用域错误（`X is not defined`）在整局驱动下必现。

### 5.2 单帧实参比对验证信息边界

验证"每张牌只在一处可见"（信息边界）**不要用调用计数推断**。取 `draw()` 调用前后 `calls` 长度的差值得到单帧切片，从中对所有 `fillText` 取首参，与"其他 4 家每张牌的牌面文案"逐一比对——命中即泄露。这是直接验证，不是间接推断。间接推断的累计计数对 20000 次和 128 次没有区分力。

### 5.3 无头测试验不到什么（报告口径）

| 验得到 | 验不到 |
|---|---|
| 作用域错误 / 未定义符号 | 像素级视觉（手牌宽度、按钮位置） |
| 状态同步断裂（currentPlayer 与 phase 不一致） | 真机触摸坐标精度 |
| 牌张守恒 / 阶段错乱 | 帧率 / 性能 |
| 驱动循环死锁 / 非法行动 | 未 mock 的宿主 API 的真实行为 |
| 信息边界泄露 | **触达性**（按钮/手牌在真机上点不点得到）|
| 事件处理抛异常 | **判据本身对不对**（测试可能照抄了实现里抄错的判据）|
| 触摸坐标 → 命中 → 出牌 的端到端映射 (§5.4) | |

**2026-10-24 实测：三个 P0 全都逃过了全绿的 55 套件**，各自对应一类盲区：

| P0 | 为什么无头测试抓不到 |
|---|---|
| **所有按钮都点不到** | 命中函数调「生成按钮列表」拿到的是**新对象**，而 x/y/w/h 写在 draw 时的**另一份对象**上 → `x >= undefined` 恒 false。无头测试若只断「按钮中心点能命中自己」，会因为**同一个错误的对象**而假通过 —— 断言必须检查**命中与布局用的是同一份数据** |
| **phase=PLAY 但按钮全灰 + AI 不出手** | 「跳到下一阶段」的按钮在该阶段**消失**了 → 最后一档永远到不了 → `currentPlayer` 恒为 null。症状是**状态不可达**，不是渲染错。要断的是**可达性不变量**：`phase===PLAY ⟹ currentPlayer !== null` |
| **持双大A 却被判无反A资格** | 引擎判据一直是对的，错的是**新写的 UI 层资格判定**把花色限定成主A的花色 —— 而**测试照抄了这个错判据**，于是全绿。**测试验证的是「实现与测试一致」，不是「实现与规则一致」** |

**结论**：无头测试能证明「实现自洽」，证明不了「实现正确」。**触达性**只有真机能验；
**判据**只有对照规则原文能验；**可达性**要写不变量断言，不能靠截图看。

**说**"无头测试 N/N 通过，IDE 目视未做"，**不要说**"画面正常"。IDE 可用时仍按 §4 第 4 条目视——那是在无头测试之上的补充，不是替代。

### 5.4 触摸坐标 → 实体命中 → 出牌 的端到端映射

§5.2 验证的是**渲染输出**（信息不该流到哪里去），**输入**方向也要验证——触摸坐标必须能命中正确的牌，并驱动引擎打出那张牌。坐标→实体映射错的话，玩家点 A 位置却选中 B 牌，UI 完全无感，引擎测试也救不了。

这条针对一切带 hitbox 的 UI（牌池、卡片列表、按钮网格、地图格），本项目小牌面用 25px 间距、无重叠 hitbox 是直接挡此类 bug 的硬约束。

**四档必测**：

1. **hitbox 几何**（[§2.1 列表/日志几何](#21-列表日志几何行数--间距--起点-联动) 的输入对应面）
   - 数量与实际手牌数一致 / 尺寸全画布一致 / 全在画布内
   - 相邻 hitbox **不重叠**（重叠会让命中测试取第一个，导致点右牌却选中左牌）
   - 居中：左右留白差 ≤1px
   - 手牌满时（22 张 × 25px = 549px）不溢出常见横屏宽度
2. **命中测试**
   - 每张 hitbox 的中心点 → 命中对应那张
   - 每张 hitbox 的左右边缘 0.5px 也命中同一张（防 off-by-one）
   - hitbox 之间的间隙 / 区外 → 不选中
3. **选择、取消、多选** —— 重复点同一张取消；可多选；选中项互不重复
4. **完整链路** —— 点两张 3 → 调 `doPlay()` → 手牌恰减 2 张、该对子已离手、牌型 = `PAIR`

**防误触**：`hitbox` 只在「人类回合 + PLAY 阶段」注入。AI 回合和 GAME_END 注入会引起"点击按钮区也选中牌"的诡异 bug。手动验：
```js
gmod.__setState(st, { currentPlayer: 'B', human: 'A' }); // AI 回合
gmod.draw();
assertEqual(hitboxes.length, 0);    // 必须不注入
st.phase = 'GAME_END';
gmod.draw();
assertEqual(hitboxes.length, 0);    // 非 PLAY 也不注入
```

**常见坑：异步坐标映射不一致**。`onTouchStart` 处理器把 `clientX/Y` 转 hitbox 时若用了**画布 devicePixelRatio** 而非 CSS 像素，真机 / 模拟器会分别命中不同的牌——把转换全用 CSS 像素（mock 里直接传 `clientX/Y` 即可）。

**为什么跑得到这一步、IDE 还看不到的事**：触摸映射是 UI 与引擎之间最容易断的契约之一。无头测试只需借助已有的 `mock-wx.js` + `fireTouch(handlers, x, y)`（§0 已记录触摸处理器），成本比目视低得多，能把"点了没反应 / 点了出错的牌"两类 bug 从 "IDE 反复复现" 降级到 "CI 一次性捕获"。
